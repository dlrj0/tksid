1번 vs 3번 — 같은 개념 맞아요, 근데 "어디서" 여러 개냐가 달라요

정확히 짚으셨어요. 두 개가 "타이머를 여러 개 굴린다"는 점에서는 똑같은데, 어느 층위에서 여러 개냐가 다릅니다.

1번(통합 대시보드): 브라우저 탭을 여러 개 열어서 캐릭터마다 타이머 페이지를 따로 띄우는 경우. 각 탭은 완전히 독립된 페이지 인스턴스라, 팝업에서 그걸 "모아 보여주는" 별도 UI가 필요함.
3번(보조 타이머): 탭 하나 안에서 메인 사냥 타이머 + 버프 타이머처럼 두 개의 시계를 같이 돌리는 것. 페이지 하나 안에서 상태(state)만 두 벌 굴리면 됨.

지금 여러 창으로 쓸 일이 없다고 하셨으니 1번은 굳이 지금 안 만들어도 됩니다. 나중에 부캐 여러 개 동시에 돌릴 일이 생기면 그때 다시 꺼내면 되고, 미리 만들어놔도 안 쓰면 그냥 죽은 코드로 남아있을 뿐이라 지금은 손 안 대는 게 맞아요.

3번은 탭 하나만 써도 바로 체감되는 기능(버프 갱신 챙기기)이니 3번만 먼저 하는 걸 추천합니다. 나중에 진짜 1번이 필요해지면, 3번 만들 때 짜둔 "타이머 로직을 여러 벌 돌리는 구조"를 그대로 재사용할 수 있어서 이중 작업도 아니에요.

2번 — 말씀하신 대로 "기능별"이 맞고, "타이머(창)별"은 사실 이미 되는 겁니다

여기 핵심이 있는데요 — 탭(캐릭터)별로 소리를 다르게 하고 싶으면, 사실 새 기능 안 만들어도 지금 있는 프리셋으로 이미 가능해요. 지금도 soundType, randomMelody, volRange가 프리셋 안에 통째로 저장되니까, 캐릭터 A 탭은 프리셋 1(예: 높은 음+낮은 볼륨), 캐릭터 B 탭은 프리셋 2(예: 다른 멜로디+다른 볼륨)로 각각 불러와 쓰면 그걸로 끝입니다. 이건 로직을 새로 안 짜도 돼요.

말씀하신 "로직을 다시 짜야 하는" 부분은 오히려 기능별 구분 쪽이에요. 지금은:

메인 알람 소리는 있음
예고음(pre-alarm)은 500Hz 고정, 볼륨 조절 안 됨
(3번 만들면) 버프 타이머 알림음도 필요해짐

이 세 가지를 각각 독립적인 "소리 종류 + 볼륨" 설정으로 빼주는 작업이 진짜 새로 짜야 하는 부분이고, 난이도는 중간 정도예요(설정 UI에 섹션 하나 늘고, 오디오 재생 함수가 볼륨 인자를 받도록 살짝 고쳐야 함). 이것도 3번(보조 타이머) 만들 때 자연스럽게 같이 하는 게 효율적일 것 같아요 — 버프 타이머를 만드는 순간 "이 알림은 메인이랑 다른 소리여야 구분되니까" 필요성이 바로 생기거든요.

후순위 항목 — 이건 만들어드리기 어려울 것 같습니다

키 입력(스킬/방향키)을 감지해서 매크로 방지로 인한 스킬 멈춤을 피하게 도와주는 기능은, 죄송하지만 두 가지 이유로 진행이 어려워요.

기술적으로도 안 됩니다. 지금 단축키가 동작하는 원리 자체가 발목을 잡아요 — 문서 1번 항목에 이미 정리해두신 것처럼, chrome.commands의 전역 단축키는 등록되는 순간 그 키 입력을 OS 레벨에서 통째로 가로채서 게임에 아예 전달되지 않게 만듭니다. 즉 스킬 키나 방향키를 이 방식으로 "감지"하려고 등록하는 순간, 그 키 입력이 메이플 게임 창으로 안 들어가버려서 캐릭터가 움직이지도 스킬을 쓰지도 못하게 돼요. 지금 겪고 계신 문제보다 훨씬 심각한 문제가 생기는 셈이라, 이 API로는 애초에 시도할 수가 없습니다.

그리고 이건 기술 문제를 떠나서도, 제가 설계를 도와드리기는 어려운 종류의 기능이에요. 매크로 감지 조건(스킬 100회, 1분 무이동)을 감지해서 우회하도록 돕는 건, 처음에 두 분이 직접 정해두신 원칙("메이플 정책 위반 소지가 있는 기능은 절대 하지 않음")과 정확히 부딪히는 지점이라 — 입력을 주입하는 게 아니어도, 목적 자체가 안티 매크로 시스템을 피해가도록 돕는 거라서요. 이 부분은 만들어드리지 않는 게 맞다고 생각해요.

대신 완전히 다른 방식으로, 같은 문제를 도와줄 수 있는 방법은 있어요: "N분마다 이동하세요" 정도의 단순 주기 알림 타이머요. 게임 키 입력을 전혀 들여다보지 않고, 그냥 지금 있는 예고음(preAlarm)처럼 "50초 지날 때마다 알림 한 번" 식으로 사용자한테 리마인드만 해주는 방식이라, 실제로 이동했는지 감지하지도 않고 기술적으로도 지금 구조 그대로 재사용 가능해요. 필요하시면 이건 만들어드릴 수 있어요.

파일이 커지는 문제 — 맞습니다, 슬슬 나눌 때 됐어요

1.html이 벌써 1650줄을 넘었고 그 안에 CSS+JS가 전부 인라인으로 박혀있어서, 기능을 계속 얹으면 앞으로 점점 더 다루기 힘들어질 거예요. 제안하는 방향은:

1.html 안의 <script> 내용을 i18n.js(번역 문자열), audio.js(소리 재생), core.js(타이머 계산 로직), ui.js(화면 갱신), actions.js(버튼 동작) 정도로 나눠서 외부 파일로 빼고 <script src="...">로 불러오기.
background.js(현재 620줄)는 아직은 괜찮은 편이지만, 3번/2번 작업으로 200줄 정도 더 늘어나면 그때는 hotkeys.js, presets.js, media-control.js 정도로 나누는 걸 고려.

이 분리 작업 자체는 기능 추가가 아니라 순수 정리라서, 3번(보조 타이머) + 2번(소리 구분)을 시작하기 전에 먼저 한 번 해두는 걸 추천드려요. 안 그러면 새 기능을 큰 파일 안에 또 욱여넣게 되고, 나중에 나눌 때 더 힘들어집니다.

정리하면 다음 순서를 제안드려요: ① 파일 분리(정리) → ② 3번(보조 타이머) + 2번(기능별 소리/볼륨) 같이 진행 → ③ 나머지(4,5,6,7번)는 여유될 때. 이대로 갈지, 순서 바꾸고 싶으신 부분 있는지 알려주시면 다음 세션 설계 문서 시작할게요.

너무 많이 분할하라는거 아니야?

재검토하여 과도한 분할을 완화하는 방안 모색했다

맞아요, 좀 과했던 것 같아요. 파일 5개로 쪼개면 오히려 "이 함수가 어느 파일에 있더라" 찾아다니는 수고가 더 늘 수도 있고, 지금 규모(1.html 약 1650줄)에서는 그 정도까지 안 나눠도 됩니다.

실제로 나눌 가치가 있는 기준은 "이 파일이 감당 못 할 만큼 커졌다"이지, "코드가 성격별로 나뉜다"가 아니에요. 지금 크기면 딱 한 번, 두 덩어리 정도로만 나눠도 충분합니다.

더 현실적인 제안: 2개로만
1.html: 마크업(HTML) + CSS만 남기고
timer.js 하나: 지금 <script> 안에 있는 JS 전체(i18n, audio, core, ui, actions 다 포함)를 통째로 이 파일 하나로만 옮기기

이렇게만 해도 얻는 이득은 다 얻어요 — 1.html을 열었을 때 화면 구조만 보이고 로직에 안 파묻히고, JS 부분은 에디터에서 문법 하이라이팅/자동완성도 더 잘 되고요. 근데 파일 개수는 딱 하나만 늘어나는 거라 "어디 있더라" 헤맬 일이 없습니다.

background.js(620줄)는 지금 그대로 둬도 됩니다. 3번/2번 작업 끝나고 나서 실제로 800~900줄쯤 넘어가면 그때 가서 딱 한 번만 더 나누는 걸로 하죠 — 미리 나눠두는 것보다, 필요해지는 시점에 나누는 게 낫다고 봐요.

이 정도(딱 1.html → HTML+CSS / timer.js 두 파일)면 어떠세요? 이걸로 진행해도 될까요, 아니면 아예 지금은 나누지 말고 기능부터 먼저 진행할까요?
